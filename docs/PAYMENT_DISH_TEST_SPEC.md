# 白盒测试用例设计说明书 (支付与菜品管理)

## 1. 概述
本文档针对 HZCU-Order 系统的**支付处理** (`PaymentService`) 与**菜品管理** (`DishService`) 进行白盒测试设计。通过覆盖不同的业务分支和状态转换，确保逻辑的严密性。

---

## 2. 支付处理逻辑 (`PaymentService`)

### 2.1 逻辑路径分析
- **分支 A (余额支付检查)**:
    - `channel == "BALANCE"` 且 余额不足 -> 抛出 `RuntimeException`。
    - `channel == "BALANCE"` 且 余额充足 -> 扣除余额并保存用户。
- **分支 B (支付记录生成)**:
    - 无论何种渠道，均需生成 `PaymentRecord` 并保存。
- **分支 C (订单状态同步)**:
    - 调用 `orderService.updateOrderStatus` 将订单改为 `PAID`。

### 2.2 测试用例设计
| 编号 | 场景描述 | 覆盖路径 | 预期结果 |
| :--- | :--- | :--- | :--- |
| **PAY-TC-01** | 余额支付成功 | 余额充足分支 | 用户余额减少，订单状态更新 |
| **PAY-TC-02** | 余额支付失败 | 余额不足/空分支 | 抛出"余额不足"异常 |
| **PAY-TC-03** | 微信支付 (Mock) | 跳过余额扣减分支 | 不扣除余额，直接生成记录并更新订单 |

---

## 3. 菜品管理逻辑 (`DishService`)

### 3.1 逻辑路径分析
- **分支 D (逻辑删除)**:
    - 验证 `deleteDish` 不是物理删除，而是将 `isDeleted` 设为 `1`。
- **分支 E (分类解析 - 内部私有方法逻辑)**:
    - 验证 `addDish` 时，如果分类不存在是否能正确处理（涉及 `resolveCategory` 逻辑）。
- **分支 F (缓存一致性)**:
    - 验证通过 `@CacheEvict` 注解关联的操作逻辑。

### 3.2 测试用例设计
| 编号 | 场景描述 | 覆盖路径 | 预期结果 |
| :--- | :--- | :--- | :--- |
| **DISH-TC-01** | 逻辑删除验证 | `deleteDish` 路径 | 数据库记录仍在，但 `isDeleted=1` |
| **DISH-TC-02** | 菜品状态更新 | `updateDishStatus` | 状态字段从 `1` 变更为 `0` |
| **DISH-TC-03** | 新增菜品默认值 | `addDish` 路径 | 自动补全 `isDeleted=0` 和 `status=1` |

---

## 4. 验证策略
- 使用 **Mockito** 验证关联保存方法的调用次数（`verify(userRepository, times(1)).save(...)`）。
- 断言实体对象在内存中的属性变更。
