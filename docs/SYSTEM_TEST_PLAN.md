# 系统测试与集成测试方案

## 1. 集成测试方案 (Integration Testing)
集成测试关注模块间的交互。我们将采用 **Spring MockMvc** 进行“窄集成测试”，测试从 Controller 到 Service 层再到 DTO 转换的完整链路。

### 1.1 测试目标
- **用户流集成**: 模拟从登录到获取个人信息的完整 API 调用链。
- **订单流集成**: 验证创建订单接口在内部如何正确调用 Service 并生成 DTO 返回。

### 1.2 技术选型
- **框架**: JUnit 5, Spring Boot Test, MockMvc
- **数据库**: Mock Repository 层以避免对本地 MySQL 的依赖，确保测试的可移植性。

---

## 2. 系统测试方案 (System/E2E Testing)
系统测试模拟真实用户在前端（小程序/Web）的操作行为，验证系统的端到端功能。

### 2.1 测试场景：用户完整订餐链路
1.  **身份认证**:
    - 调用微信登录接口，验证是否返回正确的 JWT 令牌。
2.  **商家与菜品浏览**:
    - 验证食堂列表接口是否能正确过滤已下架/逻辑删除的食堂。
    - 验证菜品详情是否包含正确的规格信息。
3.  **核心业务流**:
    - **步骤1**: 用户余额充值。
    - **步骤2**: 选择菜品提交订单，选择“余额支付”。
    - **步骤3**: 检查返回的 `orderNo` 和状态是否为 `PAID`。
    - **步骤4**: 再次查询余额，验证扣款是否准确。

### 2.2 测试场景：商户/管理端操作
1.  **商户接单**:
    - 商户登录系统。
    - 查看新进订单，将状态从 `PAID` 变更为 `PREPARING`。
    - 用户端验证订单状态更新。

## 3. 测试用例矩阵 (Testing Matrix)

| ID | 测试级别 | 测试模块 | 输入/操作 | 预期输出 |
| :--- | :--- | :--- | :--- | :--- |
| **INT-01** | 集成测试 | 用户模块 | GET /api/v1/users/me (带有效Token) | 返回 200 及用户余额信息 |
| **SYS-01** | 系统测试 | 下单支付 | 充值 100 -> 下单 30 -> 余额支付 | 订单状态 PAID，余额剩余 70 |
| **SYS-02** | 系统测试 | 商家管理 | 下订单 -> 商家端查询 | 商家端能看到该订单且 ID 匹配 |

## 4. 后续建议
建议集成 **Postman** 或 **Cypress** 进行自动化的 API 系统测试，并将其配置在 CI/CD 流水中，每次代码提交后自动运行全量回归测试。
